What gets tested

Version and lifecycle

Which release is running, whether it still receives security fixes, and whether any published advisory matches it. A release past its end of life is an F, whatever else is right.

Transport and headers

HTTPS reachability, the certificate and its remaining life, the TLS versions on offer, and the security headers a browser is actually sent - HSTS, CSP, frame and content-type protection.

Hardening and exposure

Basic authentication, public link password and expiry policy, password rules, directory listing, exposed endpoints and anything announcing the version to the world.

What happens when you press the button

Four steps, and the third one is where the queue comes in.

  1. Your address is checked. Private, loopback and cloud metadata addresses are refused before anything connects.
  2. A scan gets a random identifier. That identifier is the only way to reach the result. There is no list of scans, and no way to guess one.
  3. It waits its turn. A fixed number of scans run at once. If they are all busy yours queues and you are told where you are in line - nothing is rejected because the service is popular.
  4. The result expires. After {{ result_ttl_minutes }} minutes the identifier stops working and the result is gone, with nothing written to disk.

What this server keeps

The address you submit, the checks you chose to waive and the result live in memory for {{ result_ttl_minutes }} minutes, under a key derived from your scan's random identifier, and are then dropped by the store itself. The operational log records that a scan was created, started and finished, identified by that random identifier alone - not the address, not the result and not your IP address, which is only ever counted as a one-way fingerprint for rate limiting.

Prefer to run it yourself? The same scanner is a command line check and a Python package. Nothing here talks to a third-party service in either case.

Scanning from a script

The form is one of two front doors; the other is JSON, and it is the same handler. 

curl -X POST https://this-service/api/scans \
     -H 'Content-Type: application/json' \
     -d '{"target_url": "opencloud.example.com", "release_track": "production"}'
curl https://this-service/api/scans/<uuid>

A submission answers 202 with the scan's identifier; polling it returns queued, running or the finished result, and 404 once it has expired. Only four fields are read - the address, the checks to waive, the release track and the output format. Anything else in the body, concurrency and timeouts above all, is rejected: how hard this server probes is not a caller's decision.
